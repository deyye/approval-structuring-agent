# 字段和证据口径 v2

单位比较保留原值，只对标准化值计算。日期按真实年月日排序。同项目以唯一代码归组，不凭同名自动合并；代码缺失时独立列示，人工确认后才能合并。阶段以批文标题为依据，文件名只显示，不决定归类。

| 字段 | 取值依据 | 缺失/冲突处理 |
|---|---|---|
| 发文机关标志 | 首页红头完整文字 | 不从正文落款补齐 |
| 发文字号 | 首页独立的当前批复文号 | 不取正文请示及引用文号 |
| 标题 | 原始标题跨行拼接 | 不补写标题原本没有的机关名 |
| 印章 | 页面图形候选，必要时视觉模型或人工确认 | 未检出为无法判断，不等于无章 |
| 印发机关 | 与印发日期邻近的版记机关 | 不以正文发文机关代替 |
| 印发日期 | 明示“印发”日期 | 不以成文日期代替 |
| 项目名称 | 标题中当前审批对象 | 保留“项目”字样，不按文件名填值 |
| 项目代码 | 四位-六位-两位-两位-六位代码 | 人工修改须通过格式校验 |
| 项目单位 | 正文明示项目业主/建设单位 | 仅收文机关推断时标记待核对 |
| 建设内容 | 主要建设内容/规模整段，含跨页内容 | 不附加概算附件的费用表 |
| 建设地点 | 项目选址/建设地点整段 | 路线保留起终点 |
| 总投资/匡算/估算/概算 | 金额及原口径 | 概算/估算不同仍提示口径变化 |
| 资金来源 | 建设资金/所需资金原句 | 保留“争取”条件措辞 |
| 建设周期 | 明示工期/周期 | 单位可换算，不借用其他阶段 |

## 动态指标

先从建设内容章节识别指标，再补充设计专篇中的面积/层高等数字属性。每条保留 `name`、原文值、标准化数值、范围上界、限定词、单位、证据及 `scope`（construction/design）。

- 面积、长度、体积、投资额、时间、速度、电力与数量单位分维度计算。
- “约”“不超过”“不少于”“以上”“以下”均保留；范围上下界不丢失。
- 1公里与1000.0米在同口径下等价；1平方米与1米不可比较。
- 建筑占地面积、总建筑面积、地上建筑面积分别列示。
- 道路路面面积与行车道/路缘带/硬路肩面积保持独立，不擅自合并。
- DN管径型号、道路桩号、标准编号、年份不作为数量指标。
- 同一指标多值时全部保留并提示冲突，允许逐条人工复核。

## 状态

`extracted` 已提取；`missing` 原文未载明；`uncertain` 页面不可读、无法证明缺失；`needs_review` 角色推断或视觉候选；`conflict` 同文多值；`reviewed` 人工已复核。

每个证据保存文本行 ID、页码、PDF bbox 和引文。人工可重新选择原文行，修订记录保存原值、原证据、新值、说明和时间。`revision` 阻止旧页面覆盖新修订。手工修订属于人的确认，并非大模型自动真实性证明。

## 缺失要分两种（v2.1）

空字段必须能回答「原文确实没有」还是「系统没抽到」，否则正确的缺失看起来像系统故障，
而真正的漏抽又淹没在同样的灰格里：

| `reason` | 含义 | 界面显示 | 是否计入待办 |
|---|---|---|---|
| `absent` | 已检索全文，无该要素的任何线索 | 灰色「原文未载明」 | 否，系统已核实 |
| `unextracted` | 原文有该要素的线索却未抽出 | 红色「未提取到（原文有线索）」 | 是，需人工处理 |

「印发机关」不设线索判据：它由版记结构专门定位（要求页面下半部出现独立的机关署名行），
没有候选即确属版记未署机关，不应再报「有线索未抽到」而制造假告警。

## 跨阶段比对的两种「不算变化」（v2.1）

**一、书写精度或约数差异**：同一数值因四舍五入或单位换算产生的微小差异，归入
「表述不同 / 标准值相同」，并注明极差与各阶段写法。容差由**原值的书写精度**推出
（如 13.693 公顷精度 0.001 公顷 = 10 平方米，取半格 5 平方米），带「约」等限定词时放宽一倍。
实测：`13.693公顷` 与 `136929.6平方米` 只差 0.4 平方米，`约2.31公里` 与 `2.308千米`
只差 2 米——都不应报成「内容变化」。单步差异落在容差内时，说明文案不再给出百分比。

**二、疑似同一指标（`align`）**：两行指标**数值相同、名称不同、且各出现在不同文档列**时，
标为 `align` 并提示是否合并。实测：可行性研究写「道路路面面积60637平方米」，初步设计写
「行车道、路缘带及硬路肩总面积60637平方米」——同一数值同一工程，因措辞不同被拆成两行、
各自显示「未载明」，会让审阅人得出「这个阶段没有该指标」的错误结论。

判定要求文档列**互不重叠**：同一份文档里的「涵洞7处」与「平交口7处」数值相同，
那不是跨阶段错位，不应提示。命中只标「疑似」，是否合并由人工决定。

**`align` 必须能被人工处理掉**（提交 `kind="align"`，二选一）：

| `decision` | 动作 | 效果 |
|---|---|---|
| `merge` | 把本文件里该指标改名为对方的名称 | 两行合并为一行，比对重新计算；改后同名的指标若数值相同则直接合并，数值不同的保留两条交冲突检测 |
| `keep` | 不做任何数据改动，只记录判断 | 该项不再计入待办 |

两种处理都会写入修订记录（`kind=align`，`name` 为**两名称为一组的稳定键**）。
这一点必须单独记：合并改名与「确认不合并」都不会让指标状态发生变化，只能靠历史记录
区分「还没人看过」与「已确认过、本就不是同一指标」。

> ⚠️ 若只提示不给处理入口，对齐项会永远留在待办里，项目就永远到不了「已审完」——
> 而「什么时候可以收工」正是待办总览存在的唯一理由。

## 待办总览与「审完」口径（v2.1）

| 概念 | 定义 |
|---|---|
| 待办项 | 字段状态属 `needs_review` / `conflict` / `uncertain`，或字段 `unextracted`，或指标冲突/待复核 |
| 不计入 | `absent` 的空字段（系统已按全文线索核实原文确无）；已有人工修订记录的项 |
| 项目状态 | `未开始` / `进行中` / `已审完`（待办为零） |
| 审完定义 | 该项目下**每一份**批复的待办项都处理完毕——确认为对、改值、或显式标注缺失 |

「确认缺失」也必须是一次明确动作（写入修订记录），不能靠「没人管它」就算过关。
判断某项是否已处理以**修订记录**为准，而不是只看状态——因为确认缺失也会把状态写回
`missing`，只认状态会让确认过的缺失反复回到队列里。

## 自检循环的触发与分级（v2.1）

自检循环（`app/agent_loop.py`）在自检**发现异常时**才启动，把放宽形态的认错风险限制在
本来就有问题的文档上。它补回的指标与字段：

- 一律标 `needs_review`，**不**与主干直取的 `extracted` 同级；
- 来源标记为 `agent-widen` / `agent-alt-form` / `agent-read`，界面与导出都要能分辨；
- 文档 `engine` 追加 `+agent`，`quality` 在补救之后重算，不留陈旧值。

实测 6 份真实批复主干全部正常、自检零信号，循环一次都不会启动。

## 评测边界

公开的`evaluation/gold.json`仅包含虚构演示材料的独立预期值，不包含用户真实批文。真实材料标注通过评测脚本的`--gold`指定本地私有路径，预测与原文不进Git。页码命中不等于像素级坐标准确率；候选印章不等于自动验真。不得把演示集或开发样例成绩解释为业务泛化准确率。
