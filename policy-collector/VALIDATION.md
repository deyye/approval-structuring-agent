## 二、本轮修的缺陷（都是"看着成功、实际错了"这一类）

按危害排序。前四条属于同一族：**把"我们没抓到"误当成"站点没有"**。

### 1. 列表页用正则切嵌套 `<div>`，把数据切碎了

`parse_list_generic` 原用 `re.findall(r'<(li|tr|dd|div)\b[^>]*>(.*?)</\1>', html, re.S)`
先切块再找链接。但 `<div>` 是嵌套的，非贪婪正则在**第一个** `</div>` 就截断，
外层包装 div 被当成一个"条目"，里面几十个真条目全丢。

| 站点 | 页面实际详情链接 | 修复前解析出 | 修复后 |
|---|---|---|---|
| 河北某政策栏目页 | 16 | **0 条** | 30 条 |
| 河南某政策发布页 | 20 | **1 条** | 44 条 |
| 辽宁 / 北京 / 山西 / 四川 / 贵州 / 湖南 | — | 1–3 条 | 51 / 30 / 25 / 30 / 15 / 20 条 |

修复方式：改为**以 `<a>` 为中心 + 日期就近窗口**（窗口 = 本条结束 → 下一条开始，
兜底看链接前 120 字符）。同一批省合计从 <20 条升到 246 条。
**"这两个省站点没有政策"这个结论是错的，错在我们自己。**

### 2. 抓取返回 0 条被当成成功（浙江省）

浙江首页可达、栏目也找到了，但解析出 0 条。旧代码直接 `return []`，
覆盖报告记 `status=ok / 新增 0`，日志里没有任何异常。
**这是"沉默的 0 条"**：会被读成"该站最近没发政策"，漏采直接进交付物。

现在按成因分三档独立报错：

| status | 含义 | 处理方式 |
|---|---|---|
| `js_required` | 列表由 JS 注入，静态抓不到 | 需要浏览器渲染层 |
| `parser_gap` | **页面有内容，是我们没解析出来** | **代码缺陷，必须修** |
| `failed` | 网络 / 证书 / 反爬 | 视情况人工介入 |

`parser_gap` 必须单独成档：它和 `js_required` 都是"0 条"，
但一个是"要加渲染层"、一个是"改几行正则"，混在一起会把工期估错。
本轮天津就是被这一档暴露出来的（见第 4 条）。

### 3. 源 ID 从域名首段推断，一个 ID 覆盖 10 个省

`fgw.beijing.gov.cn`、`fgw.shanxi.gov.cn`、`fgw.ln.gov.cn`… 全被算成 `prov_fgw`；
`prov_fzggw` 覆盖了 4 个省。连锁后果：`--sources` 选不中单个省、
覆盖报告按 id 归并后互相覆盖、库内无法按省统计。

修复：省份码改为显式维护（`PROVINCES` 表第二列）+ 导入时断言唯一；
历史数据用 `scripts/repair_source_ids.py` 按 region 回填（330 条，幂等）。

### 4. 地址不在 `href` 里 → 整页误判为"解析缺口"

天津某 CMS 用 `onclick="isDownLoad(this,'https://…/t20260910_7371699.html')"` 承载跳转，
页面上**没有 href 属性**。同时该站把 `<span>标题</span><span>日期</span>` 都放进 `<a>`，
日期在链接**内部**。修复后天津从 0 条 → 48 条。

### 5. 整页扫 `<a>` 把侧栏和导航收进来（引入后又被自己发现）

改成锚点中心后范围变宽，吉林省发改委的「领导分工」页（`/jggk/ldfg/`）9 条人名职务、
「机构概况」10 条处室职责被当成政策文件入库。

修复：**优先只收落在 `<li>` / `<tr>` 里的锚点**（少于 3 个时才放弃该约束）；
再加路径黑名单（`/ldfg/`、`/lingdao/`、`/jggk/`…）与标题黑名单（导航标签 + 姓名职务型正则）。
已入库的 19 条用 `scripts/prune_noise.py` 清除（判据与解析器同源，避免两处口径漂移）。

### 6. 文号只认一种形态，漏掉整类发改委令

文号有两种形态：
- **机关代字号**：`发改投资规〔2025〕1728号`、`国办发〔2026〕24号`
- **令号 / 公告号**：`2026年第44号令`、`2026年第3号公告` ← 原先完全不认

发改委令、部门公告用后者，且编号写在**标题末尾**，因此 19 条发改委令全都没有文号。
文号是去重的第二键，漏抽会削弱去重能力。
修复后 `scripts/repair_doc_numbers.py` 用库内已存标题/正文回填 21 条（无需重新抓取）。

### 7. 分类门槛过松（85% → 19%）

第一版「标题命中任一弱词即算投资类」→ 55 条里 **47 条（85%）** 被判投资类，
「特殊教育发展规划」「森林年采伐限额复函」「出境入境管理规定」全进来了。
**召回高不等于对**，四类归集因此失去意义。

根因：`项目/工程/建设` 这类词在任意长条例的**正文**里必然出现。
逐步校准：85% → 73% → 24% → **19%（判据一律限定在标题）**。

补词表后「待定」从 59 条降到 25 条（降 58%）；剩余 25 条确属真边界
（会议新闻、谅解备忘录、定价听证会公告、开发区更名批复）。

### 8. 其他

- **江西 TLS**：`UNSAFE_LEGACY_RENEGOTIATION_DISABLED` —— 站点要求旧式服务器连接，
  OpenSSL 3 默认关闭。开启 `SSL_OP_LEGACY_SERVER_CONNECT` 后从"不可达"变为
  HTTP 200 / 235KB。**这不是站点不可用，是本机 TLS 策略过严。**
  （修复后仍因首页是 JS 模板而归入 `js_required`。）
- **重判后 Excel 是旧的**：`--reclassify` 现在会自动重新导出——
  否则调完门槛发现 Excel 没变，人会以为重判没生效。
- **`coverage.json` 被单源运行覆盖**：跑 `--sources` 排查问题时会把整份覆盖报告
  重写成只剩那一个源。现改为**按源 id 合并、保留最新状态**，未跑到的源标 `stale`。

### 9. ⚠️ 清理与删除：两次误删，共 1161 条

**这是本项目唯一造成数据损失的一类失误，两次都如实记录。**

#### 事故 A：字面规则太宽，误删 59 条

| 环节 | 发生了什么 |
|---|---|
| 起因 | 陕西省发改委的 4 个「政府信息公开」目录页（`/zfxxgk/zfxxgkzd/index1.html`）被当成政策收入库，且详情标题回退成站点名「陕西省发改委」，4 条同名 |
| 我加的规则 | "以 `index` / `indexN` 结尾 ⇒ 栏目落地页" |
| 后果 | **一次删除 59 条**——辽宁等站的文章地址形如 `/fgw/zc/zcjd/2026082815040164859/index.shtml`，文章 ID 是**目录名**、文件恰好叫 `index.shtml`。被误删的包括《辽宁省通用机场布局规划（2018-2025年）》《辽宁省人民政府关于大力发展现代物流业的实施意见》《企业投资项目核准和备案管理条例》等 |
| 发现方式 | 删除清单里有明显是真政策的标题（带《》书名号、含"规划/实施意见/管理办法"），逐条看清单时察觉不对 |
| 修正 | 判据改为**看父目录有没有长数字串（≥6 位连续数字）**：有 ⇒ 文章 ID ⇒ 保留；无 ⇒ 栏目落地页 ⇒ 拒绝。加 7 个正反用例自检全部通过 |
| 补救 | 重跑全量采集补回（列表重扫 + 去重按 URL） |

#### 事故 B：通配符作用域被想窄，误删 1102 条（更严重）

| 环节 | 发生了什么 |
|---|---|
| 起因 | 事故 A 之后，为清掉残留的 2 条 `www.gov.cn` 页脚链接（"国务院客户端小程序"等） |
| 我写的 SQL | `DELETE FROM policies WHERE url LIKE '%gov.cn%' AND source_id LIKE 'prov_%'` |
| 想的是什么 | "删那 2 条 gov.cn 的页脚链接" |
| SQL 实际做的 | `%gov.cn%` 匹配**所有** `.gov.cn` 域名——每个省的站都是。**一次删掉全部省级记录 1102 条**，库内只剩国家级 586 条 |
| 发现方式 | 删完立即核对总数，发现省级归零 |
| 修正 | 一是改用 `scripts/safe_delete.py`（见下）；二是解析层加**跨站校验**（栏目链接与条目链接必须落在同一可注册域名体系内），从源头杜绝 |
| 补救 | 重跑全量采集。**注意：不能 100% 复原**——政策栏目列表是滚动的，误删时已滚出列表页的历史条目无法通过重采获得。这也是误删比"没采到"更糟的地方 |

#### 三条硬规矩（已固化为 `scripts/safe_delete.py`）

1. **不写临时 SQL 直接 DELETE**。工具强制做到：先只数不删 → 打印样本 →
   `--max N` 超限**直接拒绝**（专治通配符写宽）→ 删除前把整行备份到
   `out/deleted/*.json` → 必须显式 `--yes` 才真删。
2. **看清单时核对数量级**。事故 B 发生时脚本打印了 71KB 清单，我没看数量——
   1102 条一眼就能看出不对。
3. **删完立刻核对总数**，与删除前的数对上再干别的。

**教训的层次**：事故 A 是"判据写得太字面"，事故 B 是"想的作用域和 SQL 的作用域不是一回事"。
靠"下次小心"防不住，只能靠工具让人**做不到**误删——所以第 1 条是关键。

### 10. `--list-only` 让正文永远补不上

列表模式（只抓列表、不抓正文）会**照常入库**，于是库里多出一批"有标题、无正文"的记录。
之后跑全量时这些 URL 已在 `known` 集合里 → 被当成"已采集"跳过 → **正文永远补不回来**。
后果很隐蔽：库看着有上千条，导出到 Excel 后正文列大面积空白。

两处修正：
- `known_urls(complete_only=True)`：跳过集合只统计**已有正文**的记录，空壳记录重新参与抓取；
- 命中重复但原记录无正文时，用新抓到的详情 `enrich()` **补全**（只填原来为空的字段，
  不覆盖已有值），计入 `enriched` 而不是 `duplicates`。

本轮据此补全 200 余条记录的正文，正文覆盖率从 87% 升到 88%（含本身无正文的图解页）。

### 11. 翻页：读链接不够，还要能探测模板 + 修 base 归一化

各站翻页写法差异极大：辽宁用 `/fgw/zc/zcjd/8375b354-2.shtml`（UUID + 序号，该栏目共 7 页）、
TRS 用 `index_2.shtml`、还有站用 `?page=2`。原先按 `index_N.shtml` 猜，
**辽宁每个栏目只拿到第 1 页的 15 条**。

**第一层**：改为**从页面自身读「下一页」链接**（`next_page_url`：依次看 `tagname` 属性 →
`href` → 属性里的相对路径），猜模式只作兜底。改后辽宁单源从 **25 条升到 68 条**。

**第二层（后果更严重）**：很多 CMS 的翻页链接是 `document.write` 在**浏览器运行时**拼出来的，
静态 HTML 里根本没有 `<a href>` —— 读链接直接失效。
实测**北京市发改委**某栏目 JS 写着 `countPage = 134`（共 **134** 页），
规则是 `index.htm → index_1.htm → index_2.htm`（`.htm` 而非 `.html`），
而按文件名猜的 `index_1.html` 一律 404 ——
**每个栏目只抓到第 1 页的 15 条，数据"看着有条目"，实际少了两个数量级。**

已增加 `detect_page_template()`：逐个试候选模板，取「能抓到 + 解析出条目 +
与第 1 页内容不同」的第一个。实测北京探测到 `index_%d.htm`、重庆与陕西探测到 `?page=%d`。

**第三层（修第二层时自己引入又修掉的回归）**：`?page=2` 型翻页若把 base 拼成
`.../zfxxgk?page=2`，`urljoin` 会把 `zfxxgk` 当成**文件名**、父目录当成 `/`，
该页所有相对链接变成 `https://host/fdzdgknr/...`（少了 `/zfxxgk`）→ **整页 404**。
实测陕西省政府网因此**第 2 页起 25 条详情全部抓取失败**，而第 1 页完全正常——
症状很像"对方站点不稳定"，实际是自己地址拼错。两处修：
`apply_page_template` 对 query 型模板保留目录末尾斜杠；`parse_list_generic`
内部统一剥掉 base 的 query/fragment 再解析。

### 12. `--sources` 的逗号写法会静默不采

`argparse` 的 `nargs='*'` 只认空格分隔，写 `--sources a,b` 时整串被当成一个（不存在的）
源名，匹配不到源后打印提示并退出（退出码 1，是对的）。但**看着像跑完了，实际一个源都没采**——
我自己就这样浪费了一轮。现已在 `parse_args()` 后按 `[,，]` 拆分，两种写法都支持。

  HTTP 200 / 235KB。**这不是站点不可用，是本机 TLS 策略过严。**
  （修复后仍因首页是 JS 模板而归入 `js_required`。）

## 三、复现

```bash
cd policy-collector
.venv/bin/python run.py --max-pages 6 --detail-limit 2500 --detail-per-source 70 --sleep 0.5
.venv/bin/python scripts/prune_noise.py            # 清噪声（幂等）
.venv/bin/python scripts/repair_doc_numbers.py     # 回填令号（幂等）
.venv/bin/python run.py --reclassify --profile strict   # 重判 + 自动重导出
.venv/bin/python run.py --report                   # 库内构成 / 按地区覆盖 / 未抓到源及原因
```

产物：`out/policies.db`（SQLite 主库）、`out/policies.xlsx`（人工查阅版）、
`out/coverage.json`（各源覆盖与失败原因）。

分类档位：`--profile strict`（默认，高精度）/ `--profile broad`（含发展规划类，高召回）。

## 五、口径问题（需业务方拍板）

**分类门槛的宽严是业务判断，不是技术问题。**
任务书对「引导类」的定义里明写了"发展规划"，而国家级/省级规划文件极多，
放宽会把「国民健康规划」「全民健身计划」一并收进来。因此做成两档：

- `strict`（当前默认）：只收标题即指向投资/项目的文件 → 266 条（19%）
- `broad`：把"发展规划/方案/纲要/行动计划"类也算进来 → 召回更高，噪音同步上升

**建议**：先按 `strict` 交付，请指导员抽检 20–30 条判断是否漏收了该收的；
若有系统性漏收，改跑 `--profile broad` 或给出更精确的口径，重判只需本地一分钟。
